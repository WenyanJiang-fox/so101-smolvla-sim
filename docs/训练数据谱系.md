# 训练数据谱系：从官方基座到 24500

记录 `picklift_colors_expert/024500` 这个 checkpoint 是怎么一步步练出来的：
每一份数据怎么采的、条数帧数、喂给哪一轮、那轮的超参和产物。

时间跨度 2026-09-11 ~ 2026-09-22。

## 0. 一句话链路

```
lerobot/smolvla_base
  └─ rgb345 数据，32000 步全模型微调        -> picklift345_full/032000
       └─ resume 续训到 100000              -> picklift345_full/100000
            └─ [换机器] 换 cf_retry 数据
                 ├─ 从官方基座重来，只训专家，20000 步   -> picklift_cf_retry_expert/020000
                 │    └─ resume 到 100000（恒定 LR）    -> .../100000
                 │         └─ resume 到 200000（LR 开始降）-> .../200000   ★ 关键节点
                 │              └─ colors 数据，24500 步，只训专家
                 │                   -> picklift_colors_expert/024500      ★ 当前
                 └─ (同一份 cf_retry 数据还派生出 3 条支线，见 §4)
```

`picklift_cf_retry_expert/200000` 是后面所有实验的公共起点，**注意它不是从
picklift345_full/100000 续下来的**——它从官方基座重起（原因见 §3.5）。

### 1.1 场上长什么样（所有数据集共用）

`collect_lerobot.make_env()`：`PickConfig` + `MuJoCoPickLift-v1`，
`POOL = [red, green, blue]` 三个 `CubeObject`，`N_DISTRACTORS=2`
→ 三个全上场，目标从三个里抽，指令只有 `Pick up the red/green/blue cube.` 三种。
立方体是 nexus 默认的 `half_size=0.0125`，边长 2.5 cm（不是老场景 `sim_scene.xml`
的 40mm）。两路相机：overhead + wrist，640×480，30 fps。

`observation.state` / `action` 都是 6 维：前 5 关节用**度**，夹爪用 **0~100 百分比**
（`SO101_JOINT_NAMES = shoulder_pan / shoulder_lift / elbow_flex / wrist_flex / wrist_roll / gripper`）。
这个口径在全流程里一致，不能改。

### 1.2 rgb（300 条）

脚本 `collect_lerobot.py`，专家是脚本策略（`collect_lerobot.pick()` 四段：
悬停 → 下降 → 合爪 60 步 → 抬起），**只写成功条**，失败走 `clear_episode_buffer`。
`action` 记的是 `data.ctrl`（命令下去的目标角），不是当前关节角。

### 1.3 retry45（45 条）

同一脚本加 `RETRY=1`。一条里先朝偏 `y ± 若干 mm` 的假位置抓一次空的、张开、再抓真的。
这是整套数据里**唯一**带「抓空 → 张开 → 重抓」的样本，占比照抄参考实现的 p=0.15。

为什么它重要：cf 那 615 条每一条都只合一次爪，0 条抓空恢复。模型学到的因此是
「到点就合爪」而不是「看到方块在爪子里才合爪」。把 45 条并进去就是为了补这个。

### 1.4 rgb345（345 条）

`so101_picklift_rgb` + `so101_picklift_retry45` 直接合并。这是第一份正经训练集。

### 1.5 cf（615 条，反事实配对）

脚本 `_gen_counterfactual.py`，208 个 seed × 3 颜色 = 624 次尝试，成 615 条
（red 206 / green 204 / blue 205，199/208 个 seed 三个颜色全成功）。

做法：包了一层 `env.reset`，注入 `options={"target_index": k}`。
`PickEnv._choose_slots` 在 k 已在该 seed 抽出的 active 集合里时**只改任务名、不动布局**。
所以同一个 seed 的三条布局逐字节相同（脚本每轮实测，不一致会打 `!`），
只有指令里的颜色词不同。日志末尾确认"同 seed 三条布局逐字节一致：是"。

### 1.6 cf_retry（660 条）

cf 615 + retry45 45。这是 `picklift_cf_retry_expert` 那一轮的数据。

### 1.7 dagger（311 条）

脚本 `_collect_dagger.py`。每条先让**策略**跑到 TCP 进悬停点 40 mm，
快照整份 `qpos/qvel`，再交给专家收尾。

- 策略段：状态是策略走出来的，动作标签填**专家在该状态下的动作**（方案 B）。
  策略自己的输出照旧驱动物理，专家的答案只记不执行。
- 专家段：`collect_lerobot.run_episode` 原样录。

写进数据集的是整条轨迹。策略自己就抓成功的条不要（`clear_episode_buffer`）。
切点判据是 TCP 到"方块正上方 60mm"的距离——不能用夹爪指令（第 0 帧就闭合，
会切在第 0 帧），也不能从 `info["privileged_state"]` 读 TCP（它的长度由
observations 决定，策略环境里只有 6 维，没有 TCP）。

**采集进程不能中途 kill**：`lerobot_dataset.py` 的 `finalize()` 不跑，
footer 元数据不写进 parquet，整个数据集失效。

### 1.8 dagger2（309 条）

同 `_collect_dagger.py`。跟 dagger 的差别是**多出来的接近过程**：
dagger 那 311 条第 0 帧就在悬停点，只有专家收尾段；
dagger2 里 268 条是完整的「策略自己从初始位姿走到悬停点 + 专家收尾」，
另有 41 条策略绕住没到位、退回初始位姿只录专家段。
帧数多 56% 就是这段接近过程。颜色绑定只体现在「从初始位姿走向哪个方块」那一段，
所以只有这份数据对颜色有用，dagger 那 311 条对颜色没用。

### 1.9 colors（618 条，颜色轮换）

脚本 `collect_colors.py`，8 路并行（`_launch_colors.sh 8 13 104 colors`，
seed 104..207）。104 个 layout × 2 套配色 × 3 个钉住的目标 = 624 设计，
实收 618（6 条专家自己没抓稳）。

跟 cf 的区别在**轮换按 layout 整体做**：同一个 seed 下两套配色共用同一份物体摆位，
只有「哪个颜色占哪个槽位」变了。于是固定的 `(seed, k)` 下，两套配色
**目标位置逐位相同，只有指令里的颜色词不同**——同一个槽位在不同配色下对应不同颜色词，
所以"去第几个槽位"这条捷径不成立。

配色 = `["red","green","blue"]` 循环左移：`rgb` 和 `gbr`。

验证（`check_colors.py`）：8 个 worker 全部报 39/39 组一致、异常 0；
104 个 seed 的三个目标位置互不相同。

### 1.10 colors_retry（624 条，2026-09-22 起采）

**要解决什么问题**：`colors` 有颜色对照但 0 条抓空恢复，`retry45` 有抓空恢复但无颜色对照，
两个集合不相交。所以模型学到的「滑落之后重抓」那条分支是在**没有颜色信号**的情况下练的，
只能退回空间先验（就近抓）。实测：seed 10000、指令 blue，第一抓抓对了蓝色方块，
抓滑之后重抓去了绿色。

**骨架**：和 `colors` 完全对齐——104 layout（seed 104..207）× 2 配色 × 3 个钉住目标
= 624 槽位。这样两批能一一对上做对照。

**重抓比例 50%**（`RETRY_PROB=0.5`，约 312 条带重抓）。

- 为什么不设 `1.0`：行为克隆会把「每局先抓空一次」也学成固定动作。
- 为什么不设参考实现的 `0.15`：`retry45` 只有 45 条，被 615 条 cf 稀释到没效果。
  这次要给足样本——312 条是 retry45 的 7 倍。

**为什么不能预先筛出哪些槽位会重抓**：`prng = default_rng(seed*7919+13)` 在
`collect_lerobot.py:184` 建好之后，`:254` 那句 `prng.normal` 每触发一次扰动就消耗一次
随机数，消耗几次取决于 `PERTURB` 命中了几步。等走到 `:308` 的 `prng.random()` 时，
随机流的位置已经不可预测。所以只能全采 624 条、事后不筛。

**训练时和旧 `colors` 618 条混用** = 1242 条，重抓占比落到约 25%。纯的那一半会和旧 618
布局重复，但同一个布局「带重抓 / 不带重抓」两份正好构成对照，不算浪费。

**帧数**：重抓条实测 240 帧（`_ref/_colordemo_retry.py` 跑出来的），纯条约 127 帧
→ 624 × 183.5 ≈ 114k 帧。加上旧 618 条的 78.2k，合计约 193k 帧。

**脚本**：`_ref/_colordemo_retry.py` 是单条演示（已跑通：seed 104 / k=0 / rgb+gbr 两条，
目标位置逐位相同 `+0.2624/+0.0136/+0.0124`，指令一红一绿，各 240 帧）。
批量版本按 `collect_colors.py` 的骨架改，只多一个 `os.environ` 前置。

**为什么必须新起入口文件**：`RETRY` / `RETRY_PROB` 是 `collect_lerobot.py:106-107` 的
模块级常量，import 时定死，import 之后再改环境变量没有用。

**这次不动摩擦**：`so101_nexus/object_slots.py:157/212/241` 仍是 `friction="1 0.05 0.001"`。
爪面摩擦 1→4 确实能压滑动（老场景实测 190mm → 44mm），但改物理必须采集端和评估端一起改，
旧 618 条立刻失效。这次只解「颜色 × 重抓」一个变量——一次只改一处。

**实测结果（2026-09-23，服务器 8 路并行）**：

| 项 | 值 |
|---|---|
| 设计 | 104 layout × 2 配色 × 3 目标 = 624 条 |
| 实收 | **604 条 / 107266 帧** / 721 MB / 30 fps |
| 轮换一致性 | 8 个 worker 全部 39/39 组一致，**异常 0** |
| 触发重抓 | 252 次 |
| 其中偏着竟抓到、降级成普通条 | 22 次 |
| **真正带重抓分支的条** | **230 条（604 的 38%）** |

各 worker 设计 78 条（13 seed × 6），实收 70~78 条，耗时 17.5~21.0 分钟。

**为什么最后在服务器采而不是本地**：本机 8 核，6 路并发时写视频的 SVT-AV1 每路开
4 个编码线程、24 线程挤 8 核互相饿死，实测 3 个 worker **0% CPU** 卡死（日志停在
编码器启动横幅上）；降到 4 路才稳，但只有 3.8 条/分钟。服务器 112 核跑 8 路是
47 条/分钟，**差 12 倍**。启动脚本 `_ref/_launch_colors_retry.sh`，
等完自动合并 `_ref/_wait_and_merge_colors_retry.sh`。

**中途踩的坑**：本地第二次启动时 4 个 worker 全崩。根因是杀残留进程用错了条件——
worker 的数据集路径走 `OUT_ROOT` **环境变量**传，不在命令行里，`CommandLine -match
'colors_retry_p'` 一个都匹配不到，杀和验尸用同一个错条件就成了空确认。实际上还有
3 个旧 worker 活着占着 mp4/parquet，`rm -rf` 删不掉，新 worker 撞上残缺目录，
`LeRobotDataset.create` 的 `exist_ok=False` 直接崩。两个启动脚本都加了「删完目录
复查」这道清场检查。

## 3. 反复踩的坑（每一轮都用到）

### 3.1 不 resume 时认哪一组 LR 参数

`lerobot/configs/train.py:275-276` 只有 `not resume` 才调
`active_cfg.get_scheduler_preset()`，所以不 resume 时真正生效的是
`--policy.scheduler_*` 那一组，顶层 `--scheduler.*` 会被覆盖。
**两边写同一组值**，谁赢都对。

### 3.2 resume 时正好反过来

resume 不重建 preset，`cfg.scheduler` 直接用存档里的 `train_config.json`，
再被顶层 CLI 覆盖——这时生效的是 `--scheduler.*`。
而且 `load_scheduler_state` 会把存档里的 `base_lrs` 和 `last_epoch` 恢复回来，
`--scheduler.peak_lr` 改不动峰值。

### 3.3 `num_decay_steps` 上限就是 `--steps`

`lerobot/optim/schedulers.py` 的 `build` 开头：`num_training_steps < num_decay_steps`
时会被夹成 `num_training_steps`。写大于 `--steps` 的值一律无效。

### 3.4 恒定 LR 的写法

`decay_lr == peak_lr` → `alpha = 1` → `lambda = (1-alpha)*cos + alpha = 1`，
余弦退化成水平线。好处是上面 3.2、3.3 两个坑全部失效。

### 3.5 起点是自己的 checkpoint ≠ 视觉塔是自己的

`PreTrainedPolicy.from_pretrained` 先用官方的 `HuggingFaceTB/SmolVLM2-500M`
构造 VLM，紧接着 `_load_as_safetensor` 用 `--policy.path` 那个 checkpoint 的
**整个 state_dict 覆盖**它。所以只要起点是自己的 checkpoint，视觉塔必然是我们练过的，
跟 `train_expert_only` 设成什么无关。

第 3 轮特意换回 `lerobot/smolvla_base`，就是为了拿到一个**没被污染过的视觉塔**；
代价是动作专家也从官方起步，丢掉之前 120k 步。

实测确认（`_ref/diff_vision_weights.py`）：`picklift_cf_retry_expert/200000`
相对官方基座，`vision_model` 197 个张量 + `connector` 1 个 + `text_model` 146 个
全部 `max|Δ| = 0.00000000`，只有 `lm_expert` 145 个张量差 0.345173。
**这份 checkpoint 就是"视觉塔逐位等于官方基座"的实证**，也是第 6 轮治不了颜色绑定的根因。

### 3.6 解冻只把 `freeze_vision_encoder` 设 false 没用

`smolvlm_with_expert.py:152` 的 `set_requires_grad` 里，`train_expert_only`
那个分支会把整个 `self.vlm` 冻上，而且排在 `freeze_vision_encoder` 判断**之后**，
后写的覆盖先写的。必须先关 `train_expert_only`。

启动后看日志里的 `num_learnable_params`：

- `99880992` = 还是只训专家（参数没传进去）
- `392904096` = 解冻成功

### 3.7 eval 一触发就卡死

GPU 0%、读盘 168MB/s 不停、线程全 futex_wait。所以从第 3 轮起统一用
`--eval_steps=0` + `--dataset.eval_split=0.0`：全部数据进训练，同时回避这个老问题。

### 3.8 读训练进度必须 `tr '\r' '\n'`

tqdm 用 `\r` 覆盖写，不是换行。直接 `grep 'N/24500'` 会捞到陈旧片段
（实测过：进程已到 324 步，grep 还报 13 步）。

### 3.9 数据集任务表是 parquet 不是 json

这个 lerobot 版本写 `meta/tasks.parquet`，`info.json` 里也没有 `repo_id` 键。
`check_colors.py` 一开始就是照 `tasks.json` 写的，跑崩了才改过来。

## 5. 评估用的东西

`_ref/rollout_video.py [seed] [step] [陪衬数] [n_action_steps] [num_steps]`，
`ckpt = <PROJECT>/checkpoints/<step>/pretrained_model`。支持 `POOL` / `TASK` 环境变量
覆盖物体池和目标。

**已知命名 bug（`rollout_video.py:107`）**：
`tag = "" if task == env_task else "_alttask"`，只区分"和环境的默认目标不同"，
所以两个不同的 override 会撞同一个文件名，后跑的静默覆盖先跑的。
没改代码，每跑完一条立刻手工 `mv` 改名绕过。

`nas`（n_action_steps）从 10 改到 16 对结果没有任何影响——它只是推理参数，
不进 loss（`smolvla` 的官方参考值是 1，不是 50）。

**为什么和旧 `colors` 混着训**：`colors_retry` 自己内部就是 374 条纯的 + 230 条带重抓
（38%）。全用它的话，行为克隆有把「每局先抓空一次」也学成固定动作的风险。

比参考实现的 15% 略高，样本数（230 条）是当年 `retry45` 45 条的 5 倍。
